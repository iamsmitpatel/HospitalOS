# Changelog

## Phase 5 — HospitalOS Connect + Final Hardening (2026-10-07)

The final implementation phase: a public-facing patient portal (HospitalOS Connect) built on the unchanged Phase 1-4 foundation, plus the security/database/observability/infrastructure hardening pass the master doc's closing instructions required before calling the platform done. One new module (`connect/`) plus two small cross-cutting ones (`notifications/`, `metrics/`); everything else is additive to existing modules, not a rewrite.

- **`connect/` — HospitalOS Connect:** a Connect patient is a `User` row with `role: PATIENT, hospitalId: null` — not a separate identity system, reusing 100% of the existing JWT/refresh-token/bcrypt infrastructure. `Patient.userId` (nullable, unique **per hospital** — see the bug fix below) links a hospital-scoped clinical record to a Connect account; one account can link to many records across many hospitals, one per hospital, via either auto-creation on first booking there (`getOrCreateForConnectUser`) or an explicit claim of a pre-existing staff-created record (exact MRN+DOB+phone match, one generic anti-enumeration error for every failure mode).
  - **Discovery** (`DiscoveryController`, fully public): hospitals/departments/doctors/available-slots, gated by `Hospital.isPublic` (default `false`) AND `DoctorProfile.isPubliclyVisible` (default `true`) AND both being active — `404` either way, never revealing which condition failed. Reuses the exact same slot-computation function as the staff-side endpoint (`DoctorsService#computeAvailableSlots`, extracted once, called from both paths).
  - **Booking** (`POST /patient/appointments`): a sibling to the staff-side `create()`, not a shared method — a Connect patient has no `hospitalId` to resolve against, so the hospital comes from the chosen doctor instead. Shares the same partial-unique-index race backstop as staff booking, plus idempotency-key support (`Appointment.idempotencyKey`, `@@unique([hospitalId, idempotencyKey])`) with P2002 disambiguation between a retried key (return the original) and a genuine slot conflict (real `409`).
  - **Patient-facing queue status / medical records**: deliberately separate query surfaces from the staff-side `queue/`/`clinical/` services (not new methods bolted onto them), so patient-safety visibility rules can't be weakened by a future staff-side change: a `DRAFT` diagnosis/prescription is never shown as finalized fact, an unverified (`ENTERED`/`REVIEWED`) lab result is withheld until `VERIFIED` while the order item itself still shows, a queue-status response shows only the caller's own position (an aggregate ahead-count), never another patient's identity or token.
- **`notifications/`:** provider-neutral `NotificationsService` + `NotificationProvider` interface; `LogNotificationProvider` is the only concrete implementation (no email/SMS vendor credentials exist in this environment — an honest placeholder, not a delivery integration). Every send is recorded as an `AuditLog` row either way (`NOTIFICATION_SENT`/`NOTIFICATION_FAILED`); a provider failure never throws into the triggering request. Wired into appointment booking/cancellation and queue call-next, all fire-and-forget.
- **`metrics/`:** hand-rolled, dependency-free Prometheus counters (no `prom-client` added) — a global `MetricsInterceptor` records request count/duration per (method, route *pattern*, status) via `response.on('finish', ...)`, exposed as raw text at `/health/metrics` (bypasses the JSON envelope on purpose). `/health/live` and `/health/ready` split liveness from readiness so a transient DB blip can't look like a reason to restart the process.
- **Two bugs found and fixed during the database-integrity audit, before either shipped:**
  - `Patient.userId` was briefly a bare global `@unique` — correct that "a record is claimed by at most one account," wrong that it also made `userId` unique across the *entire table*, which would have broken booking at a second hospital for any patient who'd ever booked at a first one. Fixed to `@@unique([hospitalId, userId])`.
  - `claimExistingRecord`'s check-then-act (read "is this unclaimed," then separately `update()`) had a race where two concurrent legitimate claimants (e.g. two family members who both know the same DOB/phone) could both "succeed," the second silently overwriting the first. Fixed to an atomic conditional `updateMany(WHERE userId IS NULL)`.
  - See `/DECISIONS.md` for both.
- **Security hardening:** the global rate-limit bucket was accidentally the *strict* auth-only budget applied to every route (would have throttled Connect's own polling/browsing patterns) — split into a generous global `default` tier and a strict per-route override on exactly the four brute-force-sensitive auth endpoints. Dependency audit (`npm audit`) found two unauthenticated critical RCEs in Next.js 14.2.35 (AVIF image-optimization, Windows-hosted) — upgraded to `next@15.5.27` after confirming zero App-Router-breaking-change risk (every page already uses client-side hooks, never the server-component async APIs Next 15 changed).
- **Tenant isolation / IDOR:** confirmed every existing tenant-scoping helper checks `actor.role !== SUPER_ADMIN` explicitly, never "`hospitalId` is null" — ruling out `Role.PATIENT` (which also has a null `hospitalId`, for an unrelated reason) piggy-backing on logic written assuming only `SUPER_ADMIN` has one. New `connect-idor.e2e-spec.ts` covers the one genuinely new ownership dimension Connect introduces (patient-vs-patient, not hospital-vs-hospital). Fixed a regression in `operations-tenant-isolation.e2e-spec.ts`'s own setup, broken by this phase's `PATIENT_SELF_REGISTRATION_ONLY` change.
- **Frontend audit (`apps/web`):** one real accessibility gap fixed (a label-less search input). One real cross-cutting bug found and fixed in two places — this staff frontend predates `Role.PATIENT` and would have rendered a broken, confusing staff dashboard for a valid Connect session; `login/page.tsx` and `use-require-auth.ts` now both log a `PATIENT` session back out with a clear message instead. Verified live in a browser (the interactive-login path can't be, no backend here — but the client-side blocked-message rendering was). No Connect frontend built this phase — API-only, same precedent Phase 4 set for its own modules.
- **Database/performance:** added a missing index (`QueueEntry.patientId`, exercised by Connect's new patient-facing query pattern, previously unindexed since nothing queried it before) and fixed an N+1 in `patient-queue.service.ts` (now reads `hospitalId` off an already-`include`d relation instead of a second query per entry).
- **CI/CD, Docker, backup/DR (new this phase, none existed before):** `.github/workflows/ci.yml` — lint/build/unit-tests/e2e-tests/migrate-deploy for the API, lint/typecheck/build for the web app, using GitHub Actions' real Docker-backed Postgres/Redis service containers. This is the first point in the project where the local Docker blocker doesn't apply — every e2e file across every phase gets to actually run once this is pushed, though no run has been observed yet. Production `Dockerfile`s for both apps (multi-stage; `apps/web`'s underlying `output: 'standalone'` build was verified locally, the Docker layer itself was not — no Docker daemon here either). Migration-safety review of all six migrations (locking characteristics, `CREATE INDEX CONCURRENTLY` called out for production scale) and a documented-but-not-executed backup/restore procedure (`pg_dump`/`pg_restore`) — honestly flagged as undemonstrated, not fabricated as tested, since no live Postgres instance has existed anywhere in this project's history.
- **Permission foundation extended:** `PATIENT_PORTAL_ACCESS` (one permission for every Connect business action — profile/booking/queue/records; real authorization is per-resource ownership in each service, not a finer-grained permission split) and `HOSPITAL_PUBLIC_PROFILE_MANAGE` (deliberately narrower than `HOSPITAL_UPDATE` — lets a `HOSPITAL_ADMIN` manage their own Connect listing without the platform-level rename/deactivate power).
- **Database:** three new migrations — `20261006120000_hospitalos_connect` (public-profile fields, `User.phone`/`dateOfBirth`/`gender`, `Patient.userId`, `DoctorProfile.isPubliclyVisible`, `Appointment.idempotencyKey`), `20261006180000_queue_entry_patient_index`, `20261006190000_patient_connect_user_scoped_unique` (the bug fix above). All generated via the same `prisma migrate diff` workaround as every prior phase — **unapplied**, same Docker blocker. See `/DATABASE.md`.
- **Tests:** unit suite grew to **280/280 passing** (up from 215) — new spec files for `connect/`'s three services, `notifications/`, `metrics/` (service + interceptor), plus extensions to `patients.service.spec.ts`, `appointments.service.spec.ts`, `queue.service.spec.ts` for every Connect-facing addition and both audit-caught bug fixes. Four new e2e spec files (`connect-idor`, `connect-concurrency`, `connect-patient-journey` — the final-E2E-list's Scenario B — plus the `operations-tenant-isolation` regression fix) — written and type-checked (confirmed via an actual run that fails only at the Docker-unavailable DB-connection step, same as every other e2e file), **not executed** here.
- Reconciled `ARCHITECTURE.md`, `DATABASE.md`, `API.md`, `SECURITY.md`, `TESTING.md`, `DECISIONS.md`, `DEPLOYMENT.md`, `README.md` with all of the above.

## Phase 4 — Clinical + Laboratory + Pharmacy + Financial Core (2026-10-06)

Five new modules on top of the unchanged Phase 2/3 foundation (auth, RBAC/permissions, tenant isolation, audit, database patterns, appointments/queue): `clinical/`, `laboratory/`, `pharmacy/`, `billing/`, `payments/`. Backend only — no frontend pages this phase (see `/DECISIONS.md`).

- **`clinical/`:** `Encounter` (started only once the queue has moved an appointment to `IN_CONSULTATION`, or as a walk-in; owned exclusively by the encounter's own doctor), `VitalSigns` (nurse-recordable, append-only), `ClinicalNote` (SOAP-style, append-only correction chain via `correctsId`), `Diagnosis` and `Prescription` (DRAFT → FINALIZED → AMENDED lifecycle, amendment creates a new row via `amendedFromId` rather than overwriting a finalized record).
- **`laboratory/`:** `LabTest` catalog, `LabOrder`/`LabOrderItem` (doctor-ordered, tied to an encounter), specimen collection, result entry with **maker-checker verification** (`LAB_RESULT_VERIFY` rejects the same user who entered the result — `SELF_VERIFICATION_FORBIDDEN`), and an amendment design that works around `LabResult.labOrderItemId`'s `@unique` constraint by creating a fresh `LabOrderItem` for the correction rather than reusing the original's (see `/DECISIONS.md`). `LabOrder.status` is a 5-state rollup (`ORDERED → COLLECTED → PROCESSING → COMPLETED`, plus `CANCELLED`) computed from its items' statuses by a pure, independently-tested function (`computeLabOrderStatus`).
- **`pharmacy/`:** `Medicine` catalog, `StockBatch` inventory with **FEFO (First-Expired-First-Out)** dispensing — `DispenseService` draws from the earliest-expiring active, unexpired batch first, spanning multiple batches in one dispense request if needed, each batch's decrement done via a conditional `updateMany` (`WHERE quantityRemaining >= take`) so concurrent dispenses against the same batch can never oversell; a mid-request shortfall rolls back the whole transaction rather than partially dispensing. `StockMovement` records every quantity change (`PURCHASE`/`ADJUSTMENT`/`DISPENSE`/`RETURN`/`EXPIRED`) through one shared primitive (`StockBatchesService.applyMovement`).
- **`billing/`:** `Service` catalog with a `ServicePrice` history (the *current* price is the row with `effectiveTo: null`; setting a new price closes out the old one in the same transaction — an `InvoiceItem` never re-derives its price from a possibly-changed catalog value later). `Invoice`/`InvoiceItem` with server-computed `subtotal`/`taxAmount`/`total` using `Prisma.Decimal` throughout (never float), an atomic per-hospital `invoiceNumber` counter (`Hospital.invoiceSequence`, same pattern as MRN/queue tokens), and a `DRAFT → ISSUED → (PARTIALLY_PAID/PAID) → REFUNDED` lifecycle with `CANCELLED` only permitted while `amountPaid` is zero.
- **`payments/`:** `Payment` recording against an invoice with **idempotency-key support** (`Payment.idempotencyKey`, `@@unique([hospitalId, idempotencyKey])`) — a retried request with the same key returns the original payment rather than double-crediting the invoice, checked proactively and backstopped by catching the DB unique-constraint violation for the genuine concurrent-retry race. `Refund` against an invoice or a specific payment, both calling into `InvoicesService.applyPayment`/`applyRefund` (shared, transaction-aware primitives) to keep `Invoice.amountPaid`/`amountRefunded`/`status` consistent.
- **Permission foundation extended to 39 permissions**, narrower than Phase 3's generic "clinical operational staff" grouping: `RECEPTIONIST` never gets clinical documentation permissions, `NURSE` gets only `vitals.create` (not notes/diagnosis/prescriptions), and — same principle as `SUPER_ADMIN` — `HOSPITAL_ADMIN` gets full financial/catalog administration but **zero** access to clinical records (encounters, notes, diagnoses, prescriptions, lab orders/results). Five new role groupings added: `NURSE_PERMISSIONS`, `RECEPTIONIST_PERMISSIONS`, `PHARMACIST_PERMISSIONS`, `LAB_TECHNICIAN_PERMISSIONS`, `ACCOUNTANT_PERMISSIONS`. See `/SECURITY.md`.
- **Bug found and fixed before it shipped:** `EncountersService.create()` initially required an appointment to be `IN_QUEUE` before starting an encounter from it — but by the time a doctor can plausibly begin clinical documentation, the queue module (`queue.service.ts#startConsultation`, Phase 3, unchanged) has *already* moved the appointment to `IN_CONSULTATION`. The real precondition is `IN_CONSULTATION`, not `IN_QUEUE`; the appointment-status transition itself belongs entirely to the queue module and needed no duplicate transition inside encounter creation. Caught by tracing the actual Phase 3 queue e2e test's flow before writing Phase 4's e2e tests, not by a test failing later — see `/DECISIONS.md`.
- **Database:** 20 new tables (`encounters`, `vital_signs`, `clinical_notes`, `diagnoses`, `prescriptions`, `prescription_items`, `lab_tests`, `lab_orders`, `lab_order_items`, `lab_results`, `medicines`, `stock_batches`, `stock_movements`, `dispense_records`, `services`, `service_prices`, `invoices`, `invoice_items`, `payments`, `refunds`), `Hospital.invoiceSequence`. Six hand-added CHECK constraints (non-negative stock/money invariants) appended to the generated migration SQL, same pattern as Phase 3's partial unique index. Third migration generated (`20261006000000_clinical_lab_pharmacy_billing`) via the same `prisma migrate diff` workaround — **unapplied**, same Docker blocker as every prior migration. See `/DATABASE.md`.
- **Tests:** 13 new unit spec files (one per service across all five modules, plus the Phase 4 permission-matrix assertions added to the existing `permissions.guard.spec.ts`) — **215/215 unit tests passing** (up from 96), including the `computeLabOrderStatus`/FEFO-allocation/idempotency-retry logic exercised directly against mocked Prisma clients. 3 new e2e spec files (`clinical-tenant-isolation` extending the Phase 3 IDOR matrix to ten new resource types, `clinical-concurrency` — inventory-oversell and payment-idempotency races under real simultaneous HTTP requests, `clinical-workflow` — the full encounter→vitals→notes→diagnosis→prescription→lab→dispense→invoice→payment→refund happy path) — written and type-checked, **not executed** (same Docker blocker, re-confirmed independently this phase). The full NestJS dependency-injection graph (all 11 modules) was independently verified to compile via `Test.createTestingModule({imports:[AppModule]}).compile()`, which does not require a live database connection — this does not substitute for the blocked e2e execution, but it is independent proof the module wiring itself has no missing providers or circular dependencies.
- Reconciled `ARCHITECTURE.md`, `DATABASE.md`, `API.md`, `SECURITY.md`, `TESTING.md`, `DECISIONS.md`, `README.md`, `DEPLOYMENT.md` with all of the above.

Still outstanding, not done in this pass (out of Phase 4 scope or blocked by environment): the migration's actual application to a live database, e2e test execution, frontend pages for any Phase 4 module (explicit scope decision, see `/DECISIONS.md`), CI.

## Phase 3 — Hospital Operations Core (2026-10-06)

The operational workflow connecting Hospital → Departments → Doctors/Schedules → Patients → Appointments → Queue, built on the Phase 2 foundation (reused as-is: auth, RBAC/permissions, tenant isolation, audit, database patterns).

- **New modules:** `departments/`, `doctors/` (profile + weekly recurring schedule + one-off unavailability + computed available-slots), `appointments/` (explicit state machine, DB-level conflict prevention via a hand-added partial unique index, history-preserving reschedule, no-show), `queue/` (check-in, race-proof `call-next` via Postgres `FOR UPDATE SKIP LOCKED`, skip/requeue/start/complete/cancel, synced to appointment status).
- **Patients enhanced:** duplicate-registration detection (`POTENTIAL_DUPLICATE_PATIENT`, phone+DOB match, `confirmDuplicate` override), migrated from `@Roles()` to `@RequirePermissions()`, first unit-test coverage (`patients.service.spec.ts`).
- **Permission foundation extended:** `department.*`, `doctor.*` (incl. `doctor.schedule.manage`), `patient.*`, `appointment.*`, `queue.read`/`queue.operate`. `SUPER_ADMIN` holds the org-structure permissions (Department, Doctor) but **none** of the patient-touching ones (Patient, Appointment, Queue) — see `/DECISIONS.md` for exactly where that line falls and why.
- **Cleanup:** `RolesGuard`/`@Roles()` deleted entirely — every module had migrated to `@RequirePermissions()`, leaving it dead code that still ran on every request.
- **New shared utilities:** `common/utils/timezone.util.ts` (dependency-free IANA-timezone-aware date math, unit-tested including a DST transition), `common/utils/tenant.util.ts` (shared tenant-resolution/cross-tenant-check helpers, with a strict no-`SUPER_ADMIN`-bypass variant for clinical data).
- **Database:** `Hospital.timezone`; `Department`, `DoctorProfile`, `DoctorSchedule`, `DoctorUnavailability`, `Appointment`, `Queue`, `QueueEntry` tables; a hand-added partial unique index for appointment-slot conflict prevention. Second migration generated (`20261005120000_hospital_operations_core`) via the same `prisma migrate diff` workaround as Phase 1/2 — **unapplied**, same Docker blocker.
- **Tests:** 5 new unit spec files (departments, doctors, appointments, queue, patients services, plus a timezone-math spec) — 96/96 unit tests passing. 5 new e2e spec files (operations tenant-isolation/IDOR/security matrix, 3 dedicated concurrency tests — MRN/appointment-booking/queue-call-next, and the full admin→department→doctor→patient→appointment→queue→completion workflow test) — written and type-checked, **not executed** (same Docker blocker as all e2e tests since Phase 1).
- **Frontend (`apps/web`):** 6 new routes (`/departments`, `/doctors`, `/patients` + `/patients/[id]`, `/appointments` + `/appointments/[id]`, `/queues` + `/queues/[id]`), a shared `AppShell` nav/header component, `authedRequest()` added to the auth context so every page shares one token-aware fetch path. Queue dashboard polls every 5s (no WebSockets — master doc §75). Manually verified in a real browser (builds clean, all routes redirect correctly when unauthenticated, no console errors) against the same unreachable-API constraint as the rest of this environment.
- Reconciled `ARCHITECTURE.md`, `DATABASE.md`, `API.md`, `SECURITY.md`, `TESTING.md`, `DECISIONS.md` with all of the above.
