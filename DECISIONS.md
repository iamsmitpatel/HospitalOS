# Architecture & Engineering Decisions

Chronological log of non-obvious decisions made while building HospitalOS, and why. See also `/ARCHITECTURE.md`, `/SECURITY.md`, `/DATABASE.md`.

## 2026-10-07 — Phase 5: `Patient.userId` was briefly a global `@unique`, caught before it shipped

First written as `userId String? @unique` — "a clinical record is claimed by at most one account," which is true but incomplete: it also made `userId` unique **across the entire `patients` table**, not per hospital. Since one Connect account is explicitly designed to link to one `Patient` row at *each* hospital it visits (one MRN per hospital, same person), this would have broken the second hospital outright: `getOrCreateForConnectUser(hospitalB, user)` finds no existing row (correctly scoped to `hospitalB`), then tries to `create()` a new one with the same `userId` — which collides with the row already sitting at `hospitalA` and fails with a unique-constraint violation. A patient who had ever booked anywhere would be permanently unable to book at a second hospital. Caught during the Phase 5 database-integrity audit (task-by-task self-review, not a user report) by re-reading the actual schema rather than trusting the prior session's own summary of it. Fixed to `@@unique([hospitalId, userId])` — see migration `20261006190000_patient_connect_user_scoped_unique`. No application code needed to change: every existing query was already written as `findFirst({ where: { hospitalId, userId } })`, i.e., already correctly scoped — only the database-level constraint was wrong.

## 2026-10-07 — Phase 5: `claimExistingRecord` had a check-then-act race between "is this unclaimed?" and "claim it"

The original implementation read the record, checked `userId === null` in application code, then ran a separate `update()` to set `userId`. Two concurrent claims that both read the record as unclaimed (the realistic case: two family members who both know the same patient's MRN/DOB/phone, not just an attacker) could both pass the check, and whichever `update()` committed last would silently steal the link from the other — the loser would see a 200 success and genuinely believe they'd claimed it, while the record actually belongs to whoever won the race. Fixed to an atomic conditional write: `updateMany({ where: { id, userId: null }, data: { userId } })`, checking `result.count === 1`. A `count === 0` means someone else won between the read and this write, and is reported with the exact same generic `PATIENT_RECORD_CLAIM_FAILED` as every other failure mode — never a different error that would reveal a race even happened. See `connect-concurrency.e2e-spec.ts` for the 10-concurrent-claimants regression test (written, not yet run — see `/TESTING.md`).

## 2026-10-07 — Phase 5: the global rate-limit bucket was accidentally the strict auth-only one

`ThrottlerModule` originally had exactly one throttler, configured from `AUTH_THROTTLE_LIMIT`/`AUTH_THROTTLE_TTL_SECONDS` (intended for login/register brute-force protection) but applied globally via `APP_GUARD` — meaning *every* route, including Connect's public discovery browsing and patient-facing queue-status polling, shared the same strict 10-requests/60s budget. Caught during the Phase 5 security-hardening pass before any Connect traffic pattern hit it in practice. Split into two: a generous `default` bucket (`DEFAULT_THROTTLE_LIMIT`, 120/60s) applied globally, and the original strict budget applied *only* to `/auth/register`, `/auth/register-patient`, `/auth/login`, `/auth/refresh` via a per-route `@Throttle({ default: { limit, ttl } })` override in `auth.controller.ts`. The override reads `configuration()` through a resolver **function**, not a value captured once at module-import time — `test/rate-limit.e2e-spec.ts` mutates `process.env.AUTH_THROTTLE_LIMIT` at runtime (inside `beforeAll`, after this module is already imported) to exercise the limit with a small number, and a statically-captured value would silently ignore that override.

## 2026-10-07 — Phase 5: the Phase 2 staff frontend now actively rejects a Connect (PATIENT) session

Caught during the frontend audit: `apps/web`'s `/login` and every staff page were built before `Role.PATIENT` existed, so nothing stopped a valid Connect account from signing into the staff portal — they'd land on `/dashboard` with a hardcoded staff nav (Departments/Doctors/Patients/Appointments/Queues) that every link would 403 on. Not a security hole (the backend's `PermissionsGuard` still blocks every actual action), but a real UX/correctness bug: confusing broken-looking UI for a role the API already fully supports. Fixed in two places, not one, since a Connect session can reach a staff page two different ways: `login/page.tsx`'s submit handler checks the just-authenticated role and immediately logs back out with a clear message if it's `PATIENT` (the interactive-login path), and `use-require-auth.ts` — called by every staff page — does the same check for a session re-established via the silent-refresh-on-page-load path (e.g. a bookmarked `/dashboard` URL). No patient-facing frontend was built this phase (Connect stays API-only on the frontend side, same "backend/API this phase, frontend later" pattern Phase 4 already established) — the message says so honestly rather than attempting a partial patient UI.

## 2026-10-07 — Phase 5: no family/dependent profile delegation model

The master doc asks for "family/dependent profiles, if supported by the existing architecture." The architecture built this phase links one Connect `User` to one `Patient` row per hospital via a single-owner `Patient.userId` foreign key — there is no concept of a second account having delegated read/write access to a record it doesn't own. Building real delegation (a parent managing a child's appointments, an adult child managing an elderly parent's) needs its own data model (who delegated to whom, what scope, how it's revoked) and its own consent/authorization story — not a quick addition on top of the ownership checks this phase already relies on everywhere (`patient.userId === connectUserId`, checked the same way in every Connect service). Rather than bolt on a partial version that would complicate every one of those ownership checks for a feature that's still underspecified, it's deferred outright and documented here as an explicit scope decision, not a silently-missed requirement. A future phase adding this should expect to touch `patients.service.ts`, every Connect `getOwn*OrThrow` method, and the IDOR test suite (`connect-idor.e2e-spec.ts`) together.

## 2026-10-07 — Phase 5: structured (JSON) logging stays deferred

Flagged back in Phase 1 ("Structured logging (pino/winston) deferred ... Phase 7") and still not built: NestJS's built-in `Logger` remains text-based, tagged with a correlation ID but not machine-parseable JSON. The Phase 5 master doc explicitly asks for "structured logs" under observability. Given the scope already covered this phase (HospitalOS Connect end to end, a full security-hardening pass, a database-integrity audit that found and fixed two real bugs above, health/live/ready + a hand-rolled Prometheus `/health/metrics`), swapping the logger for pino/winston now would touch every module's call sites for a cross-cutting change with real regression risk, for a gap that doesn't block any functional requirement. Documented honestly here and in the Phase 5 report as a known gap (contributes to a READY WITH CONDITIONS verdict, not silently marked done) rather than rushed in. See `/SECURITY.md` and `/ARCHITECTURE.md`.

## 2026-10-06 — Phase 4: encounter creation's appointment-status precondition was wrong on first write, caught before it shipped

`EncountersService.create()` was first written to require an appointment be `IN_QUEUE` before starting an encounter from it, and to transition it to `IN_CONSULTATION` itself as part of encounter creation — mirroring how `appointments.service.ts#create()` transitions a fresh booking. While writing the Phase 4 e2e workflow test and re-reading the existing Phase 3 queue e2e test/`queue.service.ts` to get the setup sequence right, it became clear this was backwards: `queue.service.ts#startConsultation()` (unchanged, Phase 3) already moves the appointment from `IN_QUEUE` to `IN_CONSULTATION` the moment a called patient's consultation starts — which necessarily happens *before* a doctor can plausibly begin clinical documentation. By the time `POST /encounters` could realistically be called with a real `appointmentId`, the appointment is already `IN_CONSULTATION`, not `IN_QUEUE` — so the original check (`assertTransitionAllowed(status, 'IN_CONSULTATION')`, which only permits that transition *from* `IN_QUEUE`) would reject every legitimate call with `409 INVALID_APPOINTMENT_TRANSITION`, and the redundant transition attempt inside `EncountersService` was dead code that could never fire correctly either. Fixed to the correct precondition: encounter creation requires `appointment.status === 'IN_CONSULTATION'` (already true by the time it's called) and performs no appointment-status write of its own — that responsibility stays entirely with the queue module, which already owns it. Caught by tracing the actual end-to-end flow before writing the test that would exercise it, the same discipline the `SKIPPED`-queue-entry fix in Phase 3 used — not by a test failing later, since this was fixed before any test encoding the wrong behavior was ever run. The unit tests and DTO documentation were updated to match. See `/SECURITY.md`.

## 2026-10-06 — Phase 4: `LabResult` amendment creates a new `LabOrderItem`, not a new `LabResult` on the same item

Diagnosis/Prescription/Appointment all use the same amendment-chain shape: a self-referencing FK (`amendedFromId`/`rescheduledFromId`) on a *new row of the same type*, pointing back at the row it supersedes. Applying that identical pattern to `LabResult` doesn't work: `LabResult.labOrderItemId` is `@unique` — one result per item, for the life of that item, by design (an item represents one specimen/test execution). A second `LabResult` row can never be created with the same `labOrderItemId` as the first, so "create a new `LabResult` with `amendsId` pointing at the old one" is not just stylistically different, it's a constraint violation. The fix treats a lab-result correction as what it actually represents clinically — re-running or re-reading the test is itself a new test-execution event, not an edit to the old one's paperwork — so `amend()` creates a **new `LabOrderItem`** (same order, same test, carrying over the original's specimen metadata) and attaches the new `LabResult` to that fresh item, with `amendsId` still pointing back at the original result. The original item and its original (now `AMENDED`) result are left untouched. This was decided while writing the schema, before any service code existed for it, specifically to avoid discovering the constraint conflict mid-implementation. See `/DATABASE.md`.

## 2026-10-06 — Phase 4: `pharmacy/` validates a `PrescriptionItem` reference via a direct Prisma query, not a `ClinicalModule` import

`DispenseService.create()` needs to confirm a `prescriptionItemId` is real, belongs to the caller's tenant, and is attached to a `FINALIZED` prescription before dispensing against it. The obvious-looking option — inject `PrescriptionsService` from `clinical/` and call a method on it — was rejected in favor of `prisma.prescriptionItem.findUnique({ include: { prescription: true } })` directly inside `pharmacy/`, for the same reason `clinical/`'s own `PrescriptionsService` validates a `medicineId` via a direct Prisma query on `prisma.medicine` rather than depending on `pharmacy/` (which, at the point `clinical/` was built, didn't exist yet): both modules reference a model the *other* module owns operationally, but neither needs anything *behavioral* from the other — just "does this row exist, same tenant, right status." Importing a whole module for a single read-only existence check would create a real `ClinicalModule ↔ PharmacyModule` dependency that provides no behavioral benefit over the direct query, and — since both directions of this exact situation occur in Phase 4 (`clinical/` reads `Medicine`, `pharmacy/` reads `PrescriptionItem`) — adopting the cross-module-import pattern for one of them while using the direct-query pattern for the other would be an inconsistency with no justification. `billing/` makes the same choice for the same reason (validating a `patientId`/`encounterId` directly rather than depending on `patients/`/`clinical/`). The actual module dependency graph that *does* exist (`laboratory/ → clinical/`, `payments/ → billing/`) is reserved for cases where the dependent module calls real behavior — `assertOwnEncounter`'s ownership check, `applyPayment`/`applyRefund`'s transaction-aware balance math — not just a lookup. See `/ARCHITECTURE.md`.

## 2026-10-06 — Phase 4: lab order status is a 5-state rollup computed from its items, not a field set directly by any endpoint

`LabOrderStatus` has five values (`ORDERED, COLLECTED, PROCESSING, COMPLETED, CANCELLED`), but no endpoint ever sets four of them directly — only the explicit `cancel` action writes `CANCELLED`. The other four are recomputed from the order's `LabOrderItem` statuses after every item-level transition (specimen collection, result entry), via a small pure function (`computeLabOrderStatus`) rather than inline conditional logic duplicated at each call site. This was deliberately pulled out as a standalone, directly-unit-testable function (all five branches, including the "every item cancelled" edge case) once it became clear the rollup logic needed to run from two different places (`collectSpecimen` and `LabResultsService#create`/`#amend`, the latter in a different module) — duplicating the branching in both places risked them silently drifting apart after a future edit to one but not the other. Both call sites pass the same open database transaction to a shared `recomputeOrderStatus` method so the item-status write and the order-status write commit atomically together.

## 2026-10-06 — Phase 4: payment idempotency is checked twice — a pre-check and a DB-constraint backstop, same two-layer shape as appointment-slot booking

`CreatePaymentDto.idempotencyKey` needs "a retried request with the same key returns the original payment, never creates a second one or double-credits the invoice" to hold even when two requests carrying the same key arrive genuinely concurrently, not just sequentially. A `findUnique` check before the insert handles the common sequential-retry case cheaply, but is insufficient alone for the concurrent case — a classic read-then-write race, the exact same shape as the appointment double-booking problem Phase 3 solved with a pre-check *and* a unique index. The DB-level backstop here is `@@unique([hospitalId, idempotencyKey])` on `Payment` itself: when two concurrent requests both pass the pre-check (because neither has committed yet) and both attempt the insert, Postgres serializes them at the unique index — the first commits, the second gets a `P2002`, caught and converted into "fetch and return the now-existing row" rather than surfacing as a raw constraint error. This is a one-line variation of the exact pattern already established for `appointments_doctor_active_slot_unique` (Phase 3) and `Encounter.appointmentId` (Phase 4, this same phase) — reused rather than re-derived, once the shape was recognized as the same problem.

## 2026-10-06 — Phase 4: `HOSPITAL_ADMIN` gets financial/catalog administration but zero clinical-record access — the same line Phase 3 drew for `SUPER_ADMIN`, drawn again one tier down

Phase 3 established that `SUPER_ADMIN` is platform administration, not implicit full access — patient-touching data is excluded entirely. Phase 4 introduces financial and inventory administration (`invoice.*`, `payment.*`, `inventory.*`) that *does* plausibly belong to a hospital's own administrator — unlike org-structure/catalog data (Department, Doctor, Medicine, LabTest, Service), which was already judged "administration-adjacent" for `SUPER_ADMIN` in Phase 3, financial administration genuinely is a hospital-level concern, not a platform one, so `HOSPITAL_ADMIN` gets it in full. But granting administrative control over an invoice doesn't imply any legitimate reason to read a diagnosis — the same test applied to `SUPER_ADMIN` in Phase 3 ("would this role plausibly need this to administer the platform/hospital without seeing any individual's clinical activity") was re-applied here and landed the same way: `HOSPITAL_ADMIN_PERMISSIONS` explicitly lists every financial/catalog permission and explicitly omits every `encounter.*`/`vitals.*`/`clinical_note.*`/`diagnosis.*`/`prescription.*`/`lab_order.*`/`lab_result.*` permission, with a comment at the point of definition making the omission look deliberate rather than an oversight a future contributor might "helpfully" fix by adding them. See `/SECURITY.md` for the two-group table this produces.

## 2026-10-06 — Phase 4: `NURSE` and `RECEPTIONIST` get narrower clinical permissions than Phase 3's generic grouping implied

Phase 3's `CLINICAL_OPERATIONAL_PERMISSIONS` bucket (patient/appointment/queue access) was shared identically across `DOCTOR`, `NURSE`, and `RECEPTIONIST` — reasonable when no clinical-documentation permissions existed yet to differentiate them. Phase 4 adds exactly that differentiation master doc §51/§52 call for: `RECEPTIONIST` gets front-desk billing (`invoice.read`/`invoice.manage`, `payment.read`/`payment.manage` — but **not** `payment.refund`, reserved for `HOSPITAL_ADMIN`/`ACCOUNTANT`) on top of the Phase 3 baseline, with zero clinical-documentation permissions of any kind; `NURSE` gets `vitals.create` and `encounter.read` on top of the same baseline, but not `clinical_note.create`, `diagnosis.manage`, or `prescription.manage` — a nurse can see the encounter and record vitals, not author clinical findings. Neither role inherits from the other or from `DOCTOR`; each role's permission array is written out explicitly in full (no shared-then-extended composition beyond the common `CLINICAL_OPERATIONAL_PERMISSIONS` baseline all three still share), so a reviewer can see exactly what any one role can do without tracing an inheritance chain.

## 2026-10-06 — Phase 4: invoice/prescription/lab monetary and status arithmetic uses `Prisma.Decimal` explicitly, not plain JS numbers passed through

Every monetary field in the schema is `Decimal` (master doc §40 — never float). Prisma accepts a plain JS `number` as input for a `Decimal` column and will convert it correctly on write, but **reading** a `Decimal` field back returns a `Prisma.Decimal` instance, not a `number` — and `invoices.service.ts`'s subtotal/tax/total computation needs to add, subtract, and multiply several of these together (per-item line totals, an invoice-level discount, a tax rate) before the first write happens, not after. Doing that arithmetic with plain JS `+`/`-`/`*` on numbers coerced from `Decimal` inputs would reintroduce exactly the floating-point imprecision `Decimal` exists to avoid. The computation is instead done entirely in `Prisma.Decimal` space (`new Prisma.Decimal(value).mul(...).sub(...)`, etc.) from the first line item through the final `total`, only ever converting to a plain `number`/`string` at the DTO-response boundary (`.toString()`) — never for an intermediate calculation. The same discipline applies to `applyPayment`/`applyRefund`'s running-balance math in the same file.

## 2026-10-06 — Phase 4: `returnStock()` doesn't track cumulative returns against a single dispense, by scope decision

`DispenseRecord` has no `quantityReturned`/running-total field, and adding one would be a schema change beyond what the received Prompt 4 text's stock-batch/dispense fields specify. `DispenseService#returnStock()` therefore checks a given return's `quantity` only against the original dispense's own `quantity` field — it has no way to know (or prevent) that a previous partial return against the *same* `DispenseRecord` already happened, so two separate return calls against one dispense are not mutually bounded by each other, in principle allowing more to be "returned" in total than was ever dispensed from that specific record. This does not threaten the inventory non-negative invariant (the batch's own `quantityRemaining` CHECK constraint still holds regardless), and is not a product requirement today — flagged explicitly as a known gap in `/SECURITY.md` rather than silently shipped, with the fix (`DispenseRecord.quantityReturned Int @default(0)`, checked and incremented atomically the same way `StockBatch.quantityRemaining` already is) scoped for whenever return-accounting precision becomes an actual requirement.

## 2026-10-06 — Phase 3: removed `RolesGuard`/`@Roles()` entirely once `patients/` migrated off it

Phase 2's entry below explains why the permission foundation was added *alongside* `RolesGuard` rather than replacing it everywhere — `patients/` was deliberately left on the old mechanism since building it out further was out of Phase 2 scope. Phase 3 brings `patients/` into scope (duplicate detection, permission wiring — task-tracked explicitly), and once it moved to `@RequirePermissions()`, a `grep` for `@Roles(` across `apps/api/src` turned up zero controller usages — only the guard/decorator's own definitions. At that point `RolesGuard` was pure dead weight: it still ran as a global `APP_GUARD` on every single request, for zero behavioral effect, while leaving its implicit `SUPER_ADMIN`-always-passes bypass sitting in the codebase as a pattern the next module could copy-paste without thinking about it. Deleted `roles.guard.ts` and `roles.decorator.ts`, removed the provider registration from `app.module.ts`. All 96 unit tests and both builds (backend/frontend) still pass — this was a pure simplification, not a behavior change, since nothing referenced it anymore.

## 2026-10-06 — Phase 3: Doctor creation requires an existing `User`, not a combined account+profile endpoint

Master doc §11 separates `User` (identity) from `DoctorProfile` (professional metadata), but doesn't specify the creation API shape. Two options: (a) `POST /doctors` creates both the `User` account and the `DoctorProfile` atomically in one call (mirroring how `POST /auth/register` bootstraps a `Hospital` + admin together), or (b) `POST /doctors` only attaches a profile to an **already-existing** `User` with `role=DOCTOR` — created separately via the existing, already-tested `POST /users` endpoint. Chose (b): it means account creation (password handling, email uniqueness, role-escalation guards) has exactly one implementation in the whole codebase, not two that could drift. The frontend's Doctors page reflects this directly — it filters `GET /users` for `role=DOCTOR` accounts with no existing profile and presents them as a dropdown, with a visible note that the account must be created first under Users.

## 2026-10-06 — Phase 3: check-in collapses `CHECKED_IN` straight into `IN_QUEUE`

The master doc's example appointment flow (§32) lists `CHECKED_IN` as a distinct step between `CONFIRMED` and `IN_QUEUE`. In practice, nothing in Phase 3's actual workflow needs a persisted pause between "staff confirms the patient has arrived" and "patient has a queue entry and a token" — the natural single staff action ("check this patient in") does both at once. `AppointmentStatus.CHECKED_IN` stays in the enum and in `ALLOWED_TRANSITIONS` (so a future endpoint could use it without a migration), but no Phase 3 endpoint can reach it: `POST /queue-entries` moves `SCHEDULED`/`CONFIRMED` straight to `IN_QUEUE`, creating the `QueueEntry` in the same transaction. Documented here and in `/SECURITY.md`/`/API.md` so it doesn't read as an oversight.

## 2026-10-06 — Phase 3: `SKIPPED` queue entries are not terminal — a `requeue` action exists specifically to avoid a dead end

Initial design made `QueueEntryStatus.SKIPPED` terminal, matching how `CANCELLED` and `COMPLETED` behave. Working through the full lifecycle surfaced a real bug in that design: `QueueEntry.appointmentId` is `@unique` (one entry per appointment, intentionally — see the schema), so if `SKIPPED` were truly terminal, a skipped patient's appointment could **never** rejoin the queue — no second `QueueEntry` could ever be created for that same `appointmentId`. Real hospital front-desk workflow also doesn't treat "skip" as "this patient is gone" (that's what cancel is for) — it means "not ready yet, try again later." Fixed by adding `SKIPPED → WAITING` as the one permitted transition out of `SKIPPED`, implemented as a `requeue` action that **reuses the same row** (new token via the same atomic counter, new `joinedAt`, `skippedAt` cleared) rather than creating a second entry — so the `@unique` constraint is never at risk of being violated by the fix itself. This is the kind of thing master doc §1 ("data integrity > feature count... do not rush") is explicitly about — caught by tracing the full lifecycle before writing the service, not by a test failing later.

## 2026-10-06 — Phase 3: appointment conflict prevention needed a hand-added partial unique index, not a plain `@@unique`

A plain `@@unique([doctorProfileId, scheduledAt])` on `Appointment` would correctly prevent double-booking a slot — but would also **permanently** block that exact slot from ever being rebooked once any appointment (even a cancelled one) had used it. That's wrong: cancelling an appointment should free the slot. Prisma's schema DSL has no syntax for a partial/filtered unique index (`WHERE status NOT IN (...)`), which is what's actually needed, so the schema carries only a regular (non-unique) `@@index` for query performance, and the real constraint is appended by hand to the generated migration SQL — a documented, accepted pattern for schema features Prisma's DSL can't express. See `/DATABASE.md` for the exact SQL and `appointments.service.ts`'s `P2002`-catching code that turns a lost race into `409 SLOT_ALREADY_BOOKED`.

## 2026-10-06 — Phase 3: `call-next` uses raw SQL (`FOR UPDATE SKIP LOCKED`), not a Prisma query

Prisma's query builder has no way to express `SELECT ... FOR UPDATE SKIP LOCKED` — the standard, well-established Postgres idiom for "atomically claim one row from a shared work queue without blocking other claimants on locked rows." Simulating it with Prisma-only primitives (e.g. a transaction that reads then conditionally updates) would reintroduce exactly the race condition the mechanism exists to prevent — two concurrent callers could both read the same `WAITING` row before either writes. Used `$queryRaw` with Prisma's tagged-template parameterization (not string concatenation — still fully protected against SQL injection) for a single `UPDATE ... WHERE id = (SELECT ... FOR UPDATE SKIP LOCKED LIMIT 1) RETURNING id` statement. This is the one place in the codebase that steps outside the ORM, and it's documented at the point of use, in `/DATABASE.md`, and here, specifically because it's the exception to how every other query in this codebase is written.

## 2026-10-06 — Phase 3: timezone handling is hand-written (`Intl.DateTimeFormat` double-conversion), not a library dependency

Correct IANA-timezone-aware date math (converting a hospital-local wall-clock schedule time to the right UTC instant, accounting for DST where relevant) is normally reached for a library (`date-fns-tz`, `luxon`, etc.). Given this codebase's established pattern of minimal, deliberately-chosen dependencies (see the Prisma/NestJS/TypeScript version-pinning entries below), and that the actual mechanism needed is a well-known, small, testable technique — using `Intl.DateTimeFormat.formatToParts()` twice to compute a timezone's real offset at a specific instant, which Node's built-in ICU data resolves correctly including DST — a ~90-line dependency-free utility (`common/utils/timezone.util.ts`) was written instead, with a dedicated unit-test file that includes a DST-transition case (`America/New_York`, spring-forward 2026) specifically to catch the kind of subtle off-by-one-hour bug this category of code is known for. If the timezone-handling surface area grows significantly in a later phase (multi-timezone support beyond "the hospital's one timezone," recurring-event RRULE-style scheduling, etc.), revisit — a library becomes clearly justified past a certain complexity, and this isn't a blanket "never add a date library" stance.

## 2026-10-06 — Phase 3: a `Queue` is get-or-created on first check-in, not created through a separate manual endpoint

The master doc's conceptual API list (§56) has no `POST /queues` — only `GET /queues`, `GET /queues/:id`, and action endpoints under `/queue-entries`. A queue is a daily operational artifact (one per doctor per day) with no meaningful content before the first patient joins it, so requiring staff to explicitly "create today's queue" before anyone can check in would be ceremony with no product value. `POST /queue-entries` (check-in) does `prisma.queue.upsert()` keyed on the `@@unique([hospitalId, doctorProfileId, queueDate])` constraint — race-safe by construction (Postgres resolves the upsert's conflict atomically), so two receptionists checking in different patients for the same doctor at the same moment on a brand-new day can't create two queues.

## 2026-10-06 — Phase 3: where exactly the SUPER_ADMIN platform-vs-clinical line falls for the new modules

Phase 2 established that `SUPER_ADMIN` gets `hospital.*`/`user.*` (platform administration) but nothing clinical (§14). Phase 3 added five new modules and each one had to be placed on one side of that line or the other — not obvious by category alone. Landed on: **Department and Doctor are org-structure** (`SUPER_ADMIN` gets full access, same `resolveTenantHospitalId`/explicit-`hospitalId` pattern as Users/Hospitals) because a platform administrator plausibly needs to help a hospital set up its department list or doctor roster during onboarding/support — that's closer to "administering the platform" than "accessing a patient's data." **Patient, Appointment, and Queue are patient-touching operational/clinical data** (`SUPER_ADMIN` gets zero access, full stop) because there's no platform-administration task that requires seeing which specific patient has an appointment with which doctor at what time. This isn't a mechanical "if it references Patient, exclude it" rule either — `DoctorProfile` doesn't reference `Patient` but was still judged on the org-structure side; the test applied was "would a platform support engineer plausibly need this to help a hospital operate the platform, without seeing any individual's health-related activity."

`PermissionsGuard`/`@RequirePermissions()` was added for `users/` and `hospitals/` (master doc §13), but `patients/` still uses the original `@Roles()`. ## 2026-10-05 — Phase 2: migration generated via `prisma migrate diff`, not `migrate dev`

Docker Desktop cannot start in this environment — confirmed independently in both the Phase 0 re-audit (below) and again in Phase 2 (`docker ps` fails; `Start-Service com.docker.service` fails with "Cannot open com.docker.service service on computer '.'" — the service isn't just stopped, it's unreachable). `prisma migrate dev` requires a live database (it creates a shadow DB to diff against). `prisma migrate diff --from-empty --to-schema-datamodel prisma/schema.prisma --script` computes the same DDL from the schema file alone — no connection needed — and was used to hand-assemble a conventional `<timestamp>_init/migration.sql` + `migration_lock.toml`. ## Pinned dependency majors below the "latest" npm tag

Several packages' `latest` dist-tag pointed at versions too new to safely build on, discovered by actually running the install/build rather than assuming the newest major is safe:

- **TypeScript**: pinned to `^5.7.3`, not the `latest` tag (`7.0.2`). TypeScript 7 is the new Go-ported compiler rewrite; `ts-jest`'s peer dependency explicitly caps at `typescript <7`. Using it would have broken the test toolchain.
- **NestJS**: pinned the whole `@nestjs/*` family to the `11.x` line, not `12.x`. `@nestjs/schematics@12` requires `typescript >=6.0.0`, and TypeScript 6 only exists as a beta (`6.0.0-beta`) — there is no stable TypeScript version that satisfies both NestJS 12's schematics and `ts-jest` simultaneously. NestJS 11 has no such conflict.
- **Prisma**: pinned to `6.19.3`, not the `latest` tag (`8.0.0-rc.19`, a release candidate) and not even the newest *stable* line, `7.x`. Prisma 7 removed the conventional `datasource { url = env("DATABASE_URL") }` syntax in favor of a new driver-adapter model (`prisma.config.ts` + `@prisma/adapter-pg`) — confirmed by actually running `prisma generate` against a 7.x schema and hitting the validation error. That's a real architectural change, not a patch, and not worth taking on for the platform's foundation yet. Revisit once the adapter model is mainstream and well-documented.
- **ioredis, joi**: pinned to the established `5.x` / `17.x` lines rather than freshly-cut `6.x` / `18.x` majors, to avoid taking on unreviewed breaking changes in infrastructure-critical packages for no functional benefit.
- **uuid**: dropped entirely. `node:crypto`'s built-in `randomUUID()` covers every use case here (refresh token IDs), so there's no reason to carry an extra dependency.

**Lesson applied going forward:** always check a package's peer dependencies and actually run the install/build before trusting `npm view <pkg> version`. "Latest" is not the same claim as "stable" or "compatible with the rest of your toolchain."

## `jsonwebtoken`'s numeric `expiresIn` is seconds, not milliseconds

`src/common/utils/duration.util.ts` parses durations like `"15m"` into milliseconds (correct for `Date` math on `RefreshToken.expiresAt`). The JWT signing calls in `auth.service.ts` divide that by 1000 before passing it as `expiresIn`, because `jsonwebtoken` (via `@nestjs/jwt`) interprets a numeric `expiresIn` as seconds. Passing milliseconds directly would have made a configured 15-minute access token actually live for ~10 days — caught during the build by reading the type error closely rather than silencing it with a cast.

## `/auth/register` is bootstrap-only, not general self-registration

The master doc's API list (§13) includes `POST /auth/register`. For a hospital staff system, letting anyone self-register as any role would violate least-privilege (§10) and tenant security (§9). Implemented instead: `/auth/register` only succeeds when zero users exist in the database — it creates the first platform `SUPER_ADMIN` and then permanently closes itself (returns `403 REGISTRATION_CLOSED` thereafter). Every other account — hospital admins, doctors, staff — is created through the authenticated, RBAC-guarded `POST /users` endpoint, which forces tenant assignment server-side. `PATIENT` self-registration is explicitly out of scope until Phase 5 (HospitalOS Connect).

## Refresh tokens: httpOnly cookie, not response body

Access tokens are returned in the JSON response body (short-lived, kept client-side in memory). Refresh tokens are set as an `httpOnly`, `sameSite=strict` cookie scoped to `/api/v1/auth`, not returned in the body. This follows master doc §11/§22's "secure cookies where appropriate" guidance and reduces the refresh token's exposure to XSS relative to storing it in JS-accessible storage. Refresh tokens are further backed by a DB-resident `RefreshToken` row (SHA-256 hash, not the raw token) enabling rotation, revocation, and reuse detection — see `/SECURITY.md`.

## Cross-tenant access returns 404, not 403

When a caller requests a resource (user, hospital) that exists but belongs to a different tenant, the API returns `404 NOT_FOUND` rather than `403 FORBIDDEN`. This avoids confirming to a caller that a resource exists in a tenant they can't see (resource-enumeration hardening), while still satisfying the master doc §30 isolation matrix — the request is denied either way. Within-tenant authorization failures (e.g., a HOSPITAL_ADMIN trying to assign a SUPER_ADMIN role) still return `403 FORBIDDEN`/`ROLE_NOT_ALLOWED`, since no tenant-existence information is at stake there.

## `User.hospitalId` nullability is enforced at the application layer, not a DB constraint

`hospitalId` is nullable on `User` because `SUPER_ADMIN` is a platform-level role not scoped to any hospital. Every other role must have a non-null `hospitalId`. Prisma cannot express "NOT NULL unless role = X" declaratively, so this is enforced in `users.service.ts` (`resolveTargetHospitalId`) rather than as a database CHECK constraint. **Flagged as a hardening candidate**: a raw-SQL CHECK constraint (`role = 'SUPER_ADMIN' OR hospital_id IS NOT NULL`) could be added via a follow-up migration if defense-in-depth against application bugs becomes a priority.

## Structured logging (pino/winston) deferred

Phase 1 uses NestJS's built-in `Logger`. Per master doc §38 ("do not overengineer"), a dedicated structured-logging library is deferred to Phase 7 (production hardening / observability) rather than added speculatively now.
