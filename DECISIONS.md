# Architecture & Engineering Decisions

Chronological log of non-obvious decisions made while building HospitalOS, and why. See also `/ARCHITECTURE.md`, `/SECURITY.md`, `/DATABASE.md`.

## 2026-10-06 — Phase 3: removed `RolesGuard`/`@Roles()` entirely once `patients/` migrated off it

Phase 2's entry below explains why the permission foundation was added *alongside* `RolesGuard` rather than replacing it everywhere — `patients/` was deliberately left on the old mechanism since building it out further was out of Phase 2 scope. Phase 3 brings `patients/` into scope (duplicate detection, permission wiring — task-tracked explicitly), and once it moved to `@RequirePermissions()`, a `grep` for `@Roles(` across `apps/api/src` turned up zero controller usages — only the guard/decorator's own definitions. At that point `RolesGuard` was pure dead weight: it still ran as a global `APP_GUARD` on every single request, for zero behavioral effect, while leaving its implicit `SUPER_ADMIN`-always-passes bypass sitting in the codebase as a pattern the next module could copy-paste without thinking about it. Deleted `roles.guard.ts` and `roles.decorator.ts`, removed the provider registration from `app.module.ts`. All 96 unit tests and both builds (backend/frontend) still pass — this was a pure simplification, not a behavior change, since nothing referenced it anymore.

## 2026-10-06 — Phase 3: Doctor creation requires an existing `User`, not a combined account+profile endpoint

Master doc §11 separates `User` (identity) from `DoctorProfile` (professional metadata), but doesn't specify the creation API shape. Two options: (a) `POST /doctors` creates both the `User` account and the `DoctorProfile` atomically in one call (mirroring how `POST /auth/register` bootstraps a `Hospital` + admin together), or (b) `POST /doctors` only attaches a profile to an **already-existing** `User` with `role=DOCTOR` — created separately via the existing, already-tested `POST /users` endpoint. Chose (b): it means account creation (password handling, email uniqueness, role-escalation guards) has exactly one implementation in the whole codebase, not two that could drift. The frontend's Doctors page reflects this directly — it filters `GET /users` for `role=DOCTOR` accounts with no existing profile and presents them as a dropdown, with a visible note that the account must be created first under Users.

## 2026-10-06 — Phase 3: check-in collapses `CHECKED_IN` straight into `IN_QUEUE`

The master doc's example appointment flow (§32) lists `CHECKED_IN` as a distinct step between `CONFIRMED` and `IN_QUEUE`. In practice, nothing in Phase 3's actual workflow needs a persisted pause between "staff confirms the patient has arrived" and "patient has a queue entry and a token" — the natural single staff action ("check this patient in") does both at once. `AppointmentStatus.CHECKED_IN` stays in the enum and in `ALLOWED_TRANSITIONS` (so a future endpoint could use it without a migration), but no Phase 3 endpoint can reach it: `POST /queue-entries` moves `SCHEDULED`/`CONFIRMED` straight to `IN_QUEUE`, creating the `QueueEntry` in the same transaction. Documented here and in `/SECURITY.md`/`/API.md` so it doesn't read as an oversight.

## 2026-10-06 — Phase 3: `SKIPPED` queue entries are not terminal — a `requeue` action exists specifically to avoid a dead end

Initial design made `QueueEntryStatus.SKIPPED` terminal, matching how `CANCELLED` and `COMPLETED` behave. Working through the full lifecycle surfaced a real bug in that design: `QueueEntry.appointmentId` is `@unique` (one entry per appointment, intentionally — see the schema), so if `SKIPPED` were truly terminal, a skipped patient's appointment could **never** rejoin the queue — no second `QueueEntry` could ever be created for that same `appointmentId`. Real hospital front-desk workflow also doesn't treat "skip" as "this patient is gone" (that's what cancel is for) — it means "not ready yet, try again later." Fixed by adding `SKIPPED → WAITING` as the one permitted transition out of `SKIPPED`, implemented as a `requeue` action that **reuses the same row** (new token via the same atomic counter, new `joinedAt`, `skippedAt` cleared) rather than creating a second entry — so the `@unique` constraint is never at risk of being violated by the fix itself. This is the kind of thing master doc §1 ("data integrity > feature count... do not rush") is explicitly about — caught by tracing the full lifecycle before writing the service, not by a test failing later.

## 2026-10-06 — Phase 3: appointment conflict prevention needed a hand-added partial unique index, not a plain `@@unique`

A plain `@@unique([doctorProfileId, scheduledAt])` on `Appointment` would correctly prevent double-booking a slot — but would also **permanently** block that exact slot from ever being rebooked once any appointment (even a cancelled one) had used it. That's wrong: cancelling an appointment should free the slot. Prisma's schema DSL has no syntax for a partial/filtered unique index (`WHERE status NOT IN (...)`), which is what's actually needed, so the schema carries only a regular (non-unique) `@@index` for query performance, and the real constraint is appended by hand to the generated migration SQL — a documented, accepted pattern for schema features Prisma's DSL can't express. See `/DATABASE.md` for the exact SQL and `appointments.service.ts`'s `P2002`-catching code that turns a lost race into `409 SLOT_ALREADY_BOOKED`.

## 2026-10-06 — Phase 3: `call-next` uses raw SQL (`FOR UPDATE SKIP LOCKED`), not a Prisma query

Prisma's query builder has no way to express `SELECT ... FOR UPDATE SKIP LOCKED` — the standard, well-established Postgres idiom for "atomically claim one row from a shared work queue without blocking other claimants on locked rows." Simulating it with Prisma-only primitives (e.g. a transaction that reads then conditionally updates) would reintroduce exactly the race condition the mechanism exists to prevent — two concurrent callers could both read the same `WAITING` row before either writes. Used `$queryRaw` with Prisma's tagged-template parameterization (not string concatenation — still fully protected against SQL injection) for a single `UPDATE ... WHERE id = (SELECT ... FOR UPDATE SKIP LOCKED LIMIT 1) RETURNING id` statement. This is the one place in the codebase that steps outside the ORM, and it's documented at the point of use, in `/DATABASE.md`, and here, specifically because it's the exception to how every other query in this codebase is written.

## 2026-10-06 — Phase 3: timezone handling is hand-written (`Intl.DateTimeFormat` double-conversion), not a library dependency

Correct IANA-timezone-aware date math (converting a hospital-local wall-clock schedule time to the right UTC instant, accounting for DST where relevant) is normally reached for a library (`date-fns-tz`, `luxon`, etc.). Given this codebase's established pattern of minimal, deliberately-chosen dependencies (see the Prisma/NestJS/TypeScript version-pinning entries below), and that the actual mechanism needed is a well-known, small, testable technique — using `Intl.DateTimeFormat.formatToParts()` twice to compute a timezone's real offset at a specific instant, which Node's built-in ICU data resolves correctly including DST — a ~90-line dependency-free utility (`common/utils/timezone.util.ts`) was written instead, with a dedicated unit-test file that includes a DST-transition case (`America/New_York`, spring-forward 2026) specifically to catch the kind of subtle off-by-one-hour bug this category of code is known for. If the timezone-handling surface area grows significantly in a later phase (multi-timezone support beyond "the hospital's one timezone," recurring-event RRULE-style scheduling, etc.), revisit — a library becomes clearly justified past a certain complexity, and this isn't a blanket "never add a date library" stance.

## 2026-10-06 — Phase 3: a `Queue` is get-or-created on first check-in, not created through a separate manual endpoint

The master doc's conceptual API list (§56) has no `POST /queues` — only `GET /queues`, `GET /queues/:id`, and action endpoints under `/queue-entries`. A queue is a daily operational artifact (one per doctor per day) with no meaningful content before the first patient joins it, so requiring staff to explicitly "create today's queue" before anyone can check in would be ceremony with no product value. `POST /queue-entries` (check-in) does `prisma.queue.upsert()` keyed on the `@@unique([hospitalId, doctorProfileId, queueDate])` constraint — race-safe by construction (Postgres resolves the upsert's conflict atomically), so two receptionists checking in different patients for the same doctor at the same moment on a brand-new day can't create two queues.

## 2026-10-06 — Phase 3: where exactly the SUPER_ADMIN platform-vs-clinical line falls for the new modules

Phase 2 established that `SUPER_ADMIN` gets `hospital.*`/`user.*` (platform administration) but nothing clinical (§14). Phase 3 added five new modules and each one had to be placed on one side of that line or the other — not obvious by category alone. Landed on: **Department and Doctor are org-structure** (`SUPER_ADMIN` gets full access, same `resolveTenantHospitalId`/explicit-`hospitalId` pattern as Users/Hospitals) because a platform administrator plausibly needs to help a hospital set up its department list or doctor roster during onboarding/support — that's closer to "administering the platform" than "accessing a patient's data." **Patient, Appointment, and Queue are patient-touching operational/clinical data** (`SUPER_ADMIN` gets zero access, full stop) because there's no platform-administration task that requires seeing which specific patient has an appointment with which doctor at what time. This isn't a mechanical "if it references Patient, exclude it" rule either — `DoctorProfile` doesn't reference `Patient` but was still judged on the org-structure side; the test applied was "would a platform support engineer plausibly need this to help a hospital operate the platform, without seeing any individual's health-related activity."

## 2026-10-05 — Phase 2: permission foundation sits alongside RolesGuard, doesn't replace it everywhere

`PermissionsGuard`/`@RequirePermissions()` was added for `users/` and `hospitals/` (master doc §13), but `patients/` still uses the original `@Roles()`. This was a deliberate scope boundary, not an oversight: Prompt 2 explicitly lists patient management as out of scope ("DO NOT IMPLEMENT YET"), and the permission foundation's own design principle (§14) is that nothing should be modeled or granted "by default" — adding patient-shaped permissions to a module nobody has verified yet would be exactly the kind of premature modeling §13 warns against ("do not implement hundreds of permissions prematurely"). `patients/` can migrate to `@RequirePermissions()` when that module is actually built out.

## 2026-10-05 — Phase 2: closed a real SUPER_ADMIN clinical-access gap in an out-of-scope module

While building the permission foundation (which required deciding exactly what `SUPER_ADMIN` is allowed to do — master doc §14), reading `patients.service.ts` surfaced that `findAllForTenant` and `getTenantScopedPatientOrThrow` both skipped the hospital filter for `SUPER_ADMIN`, so a platform administrator could read any patient in any hospital. The Patients module itself is explicitly out of Phase 2 scope ("DO NOT IMPLEMENT YET: patient management"), and the general rule here is not to touch unrelated modules. This was judged different from "building" the feature: it's a two-call-site fix that closes a privilege-escalation-shaped gap directly contradicting an explicit rule in the very prompt driving this work (§14), with no schema change, no new feature surface, and no change to any passing test. Left everything else about the module (no migration applied, no tests, `RolesGuard`'s behavior for `patients/`) untouched. See `/SECURITY.md` for the before/after and `/CHANGELOG.md`.

## 2026-10-05 — Phase 2: migration generated via `prisma migrate diff`, not `migrate dev`

Docker Desktop cannot start in this environment — confirmed independently in both the Phase 0 re-audit (below) and again in Phase 2 (`docker ps` fails; `Start-Service com.docker.service` fails with "Cannot open com.docker.service service on computer '.'" — the service isn't just stopped, it's unreachable). `prisma migrate dev` requires a live database (it creates a shadow DB to diff against). `prisma migrate diff --from-empty --to-schema-datamodel prisma/schema.prisma --script` computes the same DDL from the schema file alone — no connection needed — and was used to hand-assemble a conventional `<timestamp>_init/migration.sql` + `migration_lock.toml`. This is explicitly a stopgap: it has never been proven to apply cleanly to a real Postgres instance (no migration-history table has ever been created by it), and `/DATABASE.md` is written to make that unverified status impossible to miss. The first person with real Docker access should run `prisma migrate dev` once to confirm Prisma independently derives the identical diff (no drift) before trusting this long-term.

## 2026-10-05 — Phase 2: `GET /auth/me` returns a nested `hospital` object; login/register responses don't

Master doc §26 specifies the `/me` response shape exactly, including a nested `hospital: { id, name }` — not just `hospitalId`. The pre-existing `AuthService.me()` only returned `hospitalId`, matching the `login`/`register`/`refresh` response shape (`AuthenticatedUserProfile`). Rather than changing that shared shape (which `login`/`register`/`refresh` all use, and which existing tests assert against), a separate `MeResponse` type and query (with `include: { hospital: { select: { id, name } } }`) was added just for `me()`. The frontend calls `/auth/me` once right after login/register to hydrate the full profile rather than trusting the bare login response — see `apps/web/src/lib/auth-context.tsx`.

## 2026-10-05 — Phase 2: frontend pinned to Next.js 14 + React 18, not the `latest` tag

`npm view next dist-tags` showed `latest: 16.3.8` in this environment. Following the same discipline as the backend's dependency pins (below — "always check peer deps and actually build before trusting `npm view <pkg> version`"), Next 14.2.x + React 18.3.x was chosen instead: it's the most battle-tested, longest-documented App Router combination, with no React-19-ecosystem-compatibility risk and no Next-15/16 default-behavior changes (async request APIs, Turbopack defaults) to account for in a minimal two-form-and-a-shell scaffold. Unlike the Prisma 7/8 case, nothing here indicated `next@latest` was actually unstable (no `-rc`/`-beta` suffix) — this was a stability-over-recency judgment call for a small surface area, not a correctness-driven avoidance. Revisit once the frontend has enough surface area that Next 15/16's features (e.g. partial prerendering) would matter.

## 2026-10-05 — Phase 2: frontend register page has no `hospitalName` field, unlike the generic spec example

Master doc §16 describes registration as collecting `firstName, lastName, email, password, hospitalName` and creating both a `Hospital` and its admin atomically. The *actual, already-approved* backend flow (documented below, "`/auth/register` is bootstrap-only") is different and was built in an earlier phase: `POST /auth/register` only ever creates the platform's first `SUPER_ADMIN`, with no hospital at all, and closes permanently afterward. Per the standing rule not to silently change approved architecture, the frontend was built to match what the API actually does, not the spec's generic conceptual flow — `apps/web/src/app/register/page.tsx` has no `hospitalName` field and its copy explains this is a one-time platform bootstrap screen. Hospital creation and hospital-admin/staff provisioning happen afterward via the authenticated `POST /hospitals` → `POST /users` flow, which has no frontend UI yet (out of Phase 2 scope — §44 only asks for register/login/dashboard-shell/logout).

## Pinned dependency majors below the "latest" npm tag

Several packages' `latest` dist-tag pointed at versions too new to safely build on, discovered by actually running the install/build rather than assuming the newest major is safe:

- **TypeScript**: pinned to `^5.7.3`, not the `latest` tag (`7.0.2`). TypeScript 7 is the new Go-ported compiler rewrite; `ts-jest`'s peer dependency explicitly caps at `typescript <7`. Using it would have broken the test toolchain.
- **NestJS**: pinned the whole `@nestjs/*` family to the `11.x` line, not `12.x`. `@nestjs/schematics@12` requires `typescript >=6.0.0`, and TypeScript 6 only exists as a beta (`6.0.0-beta`) — there is no stable TypeScript version that satisfies both NestJS 12's schematics and `ts-jest` simultaneously. NestJS 11 has no such conflict.
- **Prisma**: pinned to `6.19.3`, not the `latest` tag (`8.0.0-rc.19`, a release candidate) and not even the newest *stable* line, `7.x`. Prisma 7 removed the conventional `datasource { url = env("DATABASE_URL") }` syntax in favor of a new driver-adapter model (`prisma.config.ts` + `@prisma/adapter-pg`) — confirmed by actually running `prisma generate` against a 7.x schema and hitting the validation error. That's a real architectural change, not a patch, and not worth taking on for the platform's foundation yet. Revisit once the adapter model is mainstream and well-documented.
- **ioredis, joi**: pinned to the established `5.x` / `17.x` lines rather than freshly-cut `6.x` / `18.x` majors, to avoid taking on unreviewed breaking changes in infrastructure-critical packages for no functional benefit.
- **uuid**: dropped entirely. `node:crypto`'s built-in `randomUUID()` covers every use case here (refresh token IDs), so there's no reason to carry an extra dependency.

**Lesson applied going forward:** always check a package's peer dependencies and actually run the install/build before trusting `npm view <pkg> version`. "Latest" is not the same claim as "stable" or "compatible with the rest of your toolchain."

## `jsonwebtoken`'s numeric `expiresIn` is seconds, not milliseconds

`src/common/utils/duration.util.ts` parses durations like `"15m"` into milliseconds (correct for `Date` math on `RefreshToken.expiresAt`). The JWT signing calls in `auth.service.ts` divide that by 1000 before passing it as `expiresIn`, because `jsonwebtoken` (via `@nestjs/jwt`) interprets a numeric `expiresIn` as seconds. Passing milliseconds directly would have made a configured 15-minute access token actually live for ~10 days — caught during the build by reading the type error closely rather than silencing it with a cast.

## `/auth/register` is bootstrap-only, not general self-registration

The master doc's API list (§13) includes `POST /auth/register`. For a hospital staff system, letting anyone self-register as any role would violate least-privilege (§10) and tenant security (§9). Implemented instead: `/auth/register` only succeeds when zero users exist in the database — it creates the first platform `SUPER_ADMIN` and then permanently closes itself (returns `403 REGISTRATION_CLOSED` thereafter). Every other account — hospital admins, doctors, staff — is created through the authenticated, RBAC-guarded `POST /users` endpoint, which forces tenant assignment server-side. `PATIENT` self-registration is explicitly out of scope until Phase 5 (HospitalOS Connect).

## Refresh tokens: httpOnly cookie, not response body

Access tokens are returned in the JSON response body (short-lived, kept client-side in memory). Refresh tokens are set as an `httpOnly`, `sameSite=strict` cookie scoped to `/api/v1/auth`, not returned in the body. This follows master doc §11/§22's "secure cookies where appropriate" guidance and reduces the refresh token's exposure to XSS relative to storing it in JS-accessible storage. Refresh tokens are further backed by a DB-resident `RefreshToken` row (SHA-256 hash, not the raw token) enabling rotation, revocation, and reuse detection — see `/SECURITY.md`.

## Cross-tenant access returns 404, not 403

When a caller requests a resource (user, hospital) that exists but belongs to a different tenant, the API returns `404 NOT_FOUND` rather than `403 FORBIDDEN`. This avoids confirming to a caller that a resource exists in a tenant they can't see (resource-enumeration hardening), while still satisfying the master doc §30 isolation matrix — the request is denied either way. Within-tenant authorization failures (e.g., a HOSPITAL_ADMIN trying to assign a SUPER_ADMIN role) still return `403 FORBIDDEN`/`ROLE_NOT_ALLOWED`, since no tenant-existence information is at stake there.

## `User.hospitalId` nullability is enforced at the application layer, not a DB constraint

`hospitalId` is nullable on `User` because `SUPER_ADMIN` is a platform-level role not scoped to any hospital. Every other role must have a non-null `hospitalId`. Prisma cannot express "NOT NULL unless role = X" declaratively, so this is enforced in `users.service.ts` (`resolveTargetHospitalId`) rather than as a database CHECK constraint. **Flagged as a hardening candidate**: a raw-SQL CHECK constraint (`role = 'SUPER_ADMIN' OR hospital_id IS NOT NULL`) could be added via a follow-up migration if defense-in-depth against application bugs becomes a priority.

## Structured logging (pino/winston) deferred

Phase 1 uses NestJS's built-in `Logger`. Per master doc §38 ("do not overengineer"), a dedicated structured-logging library is deferred to Phase 7 (production hardening / observability) rather than added speculatively now.
