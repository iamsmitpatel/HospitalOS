# Testing

## Strategy

Per master doc §29/§30: tests exist to verify important business behavior, not to inflate a count. Unit tests cover business logic that's awkward to exercise over HTTP (tenant-derivation edge cases, token-reuse detection, the permission map, the appointment/queue state machines, timezone math); e2e tests cover everything that matters as an HTTP contract — including the **mandatory tenant isolation test**, the RBAC matrix, the security checklist, and the concurrency tests.

**Execution status (Phase 5, 2026-10-07): unit tests are run and pass (280/280); e2e tests are written but have never run *in this environment*.** Docker Desktop cannot start here (`docker ps` fails, and the underlying `com.docker.service` Windows service cannot be started either — confirmed independently in every phase, Phase 5 re-confirmed again), and `createTestApp()` eagerly calls `PrismaService.$connect()`, which hangs/fails without a live Postgres instance. Every e2e spec file below is therefore unverified by actual execution *here*. That changes once this is pushed: `.github/workflows/ci.yml` (new this phase — see `/DEPLOYMENT.md`) runs the exact same suite against real Postgres/Redis service containers on GitHub's runners, which have a working Docker daemon. Until a run of that workflow has actually been observed succeeding, treat every e2e file as reviewed-but-unproven, same as before — the workflow's existence is not the same claim as a passing run.

As independent (partial) evidence that the Phase 4 wiring itself is sound even without a database: the full NestJS dependency-injection graph for `AppModule` — all 11 modules, including the five new Phase 4 ones — was confirmed to compile via `Test.createTestingModule({ imports: [AppModule] }).compile()`, which resolves every provider and constructor dependency but does **not** call `onModuleInit()` (so it never attempts `PrismaService.$connect()`). This catches missing providers and circular dependencies; it proves nothing about the actual SQL any service executes, which is exactly what the blocked e2e suite would prove.

## Running tests

```bash
cd apps/api

npm run test          # unit tests — no database or Redis needed
npm run test:e2e      # e2e tests — needs Postgres + Redis running (docker compose up -d) and migrations applied
```

`test:e2e` sets `NODE_ENV=test` (via `cross-env`, for Windows/Mac/Linux parity), which points the app at `apps/api/.env.test` — `DATABASE_URL` there targets the separate `hospitalos_test` database created by `docker/postgres/init-test-db.sql`. **Never** point `.env.test` at `hospitalos_dev`; the e2e suite truncates every table between test files, children before parents (`test/utils/test-app.ts#resetDatabase` — extended in Phase 3 to cover `queueEntry`, `queue`, `appointment`, `doctorUnavailability`, `doctorSchedule`, `doctorProfile`, `department`, and extended again in Phase 4 to cover all 20 new tables — `refund`, `payment`, `invoiceItem`, `invoice`, `servicePrice`, `service`, `dispenseRecord`, `stockMovement`, `stockBatch`, `medicine`, `labResult`, `labOrderItem`, `labOrder`, `labTest`, `prescriptionItem`, `prescription`, `diagnosis`, `clinicalNote`, `vitalSigns`, `encounter` — deleted in FK-safe order, before the Phase 3 tables they reference).

Before running e2e tests for the first time, apply migrations to the test database:

```bash
cd apps/api
DATABASE_URL="postgresql://hospitalos:hospitalos_dev_password@localhost:5432/hospitalos_test?schema=public" npx prisma migrate deploy
```

(On Windows PowerShell: `$env:DATABASE_URL="..."; npx prisma migrate deploy`.)

**Windows note:** `npm run test:e2e` invokes `cross-env`, which in this environment failed with `'cross-env' is not recognized...` when npm dispatched the script through `cmd.exe` directly (works fine invoked other ways, e.g. from a shell that already has `node_modules/.bin` on `PATH`). If you hit this, run `npx jest --config ./test/jest-e2e.json` directly with `NODE_ENV=test` set in your shell instead. Separately: with Postgres/Redis unreachable, `createTestApp()` does not fail fast — `PrismaService.$connect()` hangs rather than throwing a quick connection-refused error, so a bad environment looks identical to a slow one until you kill the process. Worth a connection-timeout hardening pass if this keeps costing debugging time (see the Phase 2/3 reports, Known Issues).

## What's covered

### Unit (`src/**/*.spec.ts`) — executed, 280/280 passing

Phase 1/2 (unchanged): `auth.service.spec.ts`, `users.service.spec.ts`, `common/guards/permissions.guard.spec.ts` — see the Phase 2 report for details.

Phase 3 additions:

- `common/utils/timezone.util.spec.ts` — the IANA-timezone-conversion math (`zonedWallTimeToUtc`/`getZonedDateParts`) against concrete worked examples, including a DST-observing zone (`America/New_York`) on both sides of a spring-forward transition, and a near-midnight date-boundary disagreement between a local zone and UTC. - `departments.service.spec.ts` — tenant derivation (`HOSPITAL_ADMIN` ignores a client-supplied `hospitalId`; `SUPER_ADMIN` must supply a valid one), duplicate code/name conflict, cross-tenant fetch returning `404` not `403`, `SUPER_ADMIN` cross-hospital read allowed (org-structure, not clinical).
- `doctors.service.spec.ts` — profile-creation validation chain (target user must have `role=DOCTOR`, must not already have a profile, must belong to the resolved hospital), `displayName` defaulting, schedule ownership (`DOCTOR` can only manage their own schedule — `403 FORBIDDEN` for another doctor's), schedule-range and overlap validation, and the full `getAvailableSlots` computation: inclusive end-boundary slot generation, exclusion of booked/unavailable/past slots, with a controlled "now" via fake timers.
- `appointments.service.spec.ts` — `assertTransitionAllowed` tested directly and exhaustively (every terminal-state transition rejected, the master doc §32 `COMPLETED → SCHEDULED` example explicitly proven to throw, `SCHEDULED → IN_CONSULTATION` skip-ahead rejected), plus the full `create` validation chain (`SUPER_ADMIN` rejected, inactive patient/doctor rejected, past time rejected, slot-not-in-available-list rejected, a `P2002` from a lost race converted to `409 SLOT_ALREADY_BOOKED`), cancel (state-check + linked-queue-entry cleanup), reschedule (state-check + history-preserving create), no-show (future-appointment rejection).
- `queue.service.spec.ts` — check-in validation chain (appointment-state check, duplicate-entry check, token assignment, appointment sync to `IN_QUEUE`), `callNext` (the raw-SQL claim path, the `NO_WAITING_PATIENTS` empty case, cross-tenant rejection), and every entry-state transition including the `SKIPPED → WAITING` requeue with a fresh token, each verified to sync (or not sync) the linked appointment correctly.

### E2E (`test/*.e2e-spec.ts`) — written, **not executed** (see Strategy above)

Phase 1/2 (unchanged): `auth.e2e-spec.ts`, `tenant-isolation.e2e-spec.ts`, `rbac.e2e-spec.ts`, `security.e2e-spec.ts`, `concurrency.e2e-spec.ts`, `rate-limit.e2e-spec.ts` — see the Phase 2 report for details.

Phase 3 additions:

- `operations-tenant-isolation.e2e-spec.ts` — the mandatory IDOR/privacy/security matrix for every Phase 3 module (master doc §65-68). Builds a full operational graph (department, doctor + schedule, patient, appointment, queue entry) independently in Hospital A and Hospital B, then asserts: cross-tenant `404` for Department/Doctor/Patient/Appointment/Queue/QueueEntry (bidirectional — A→B and B→A); a mass-assignment attempt against `PATCH /appointments/:id` (smuggling a `status` field) rejected with `400`; a client-supplied `hospitalId` on `POST /departments` ignored; and a `Role.PATIENT` account denied every operational endpoint outright (list patients, create appointment, check in, call-next, skip) since no patient self-service exists yet.
- `patient-mrn-concurrency.e2e-spec.ts` — master doc §84. **25 simultaneous patient registrations** (reduced from the suggested 100 — meaningful concurrency pressure on the same atomic counter without a disproportionately slow test; the mechanism being proven doesn't get materially more proof from 100 vs 25), asserting 25 unique MRNs and exactly 25 persisted patients.
- `appointment-concurrency.e2e-spec.ts` — master doc §85. 10 simultaneous booking attempts for the same doctor and the exact same slot; asserts exactly 1 `201` and 9 `409`s, and exactly one non-cancelled appointment at that slot afterward.
- `queue-concurrency.e2e-spec.ts` — master doc §86. 5 waiting entries, 5 simultaneous `call-next` requests; asserts all 5 succeed and claim 5 *distinct* entries (proving `FOR UPDATE SKIP LOCKED` actually distributes claims rather than letting callers race for the same row), then asserts a 6th call-next against an now-empty queue gets a controlled `409 NO_WAITING_PATIENTS`.
- `hospital-workflow.e2e-spec.ts` — **the most important end-to-end test in Phase 3** (master doc §87). One continuous run of the full real-world flow: admin login → create department → create doctor → configure schedule → confirm the slot appears in `available-slots` → create patient (asserts the MRN format) → book appointment → confirm the slot disappears from `available-slots` once booked → check in (asserts token number, asserts the appointment flips to `IN_QUEUE`) → call next → start consultation (asserts appointment flips to `IN_CONSULTATION`) → complete the queue entry → confirm the appointment is `COMPLETED` without a separate call → confirm `COMPLETED` is terminal (a cancel attempt afterward gets `409 INVALID_APPOINTMENT_TRANSITION`). Every step asserts state before advancing, so a regression fails at the step it broke, not just at the end.

Phase 4 additions:

- `clinical-tenant-isolation.e2e-spec.ts` — extends the operations IDOR matrix to Encounter, Diagnosis, Prescription, LabOrder, LabOrderItem, LabResult, Medicine, StockBatch, Service, Invoice, Payment — ten new resource types, each checked with the role that actually holds the read permission for it (not a single uniform caller — Phase 4's narrower permission map means `DOCTOR` can read clinical resources but not inventory/billing ones, and vice versa for `HOSPITAL_ADMIN`; see `/SECURITY.md`), plus a lab-technician-specific cross-tenant check (`POST /lab-order-items/:id/collect` against another hospital's item).
- `clinical-concurrency.e2e-spec.ts` — two independent races: (1) **inventory never oversells** — 20 concurrent dispense requests of 3 units each against a 50-unit batch; asserts exactly `floor(50/3) = 16` succeed, the rest fail cleanly with `409 INSUFFICIENT_STOCK`, and the batch's final `quantityRemaining` is exactly `50 - 48 = 2`, never negative, regardless of arrival order (the FEFO loop's all-or-nothing transaction rollback makes the outcome deterministic — see `/DATABASE.md`); (2) **payment idempotency** — 10 concurrent `POST /payments` with the same `idempotencyKey` against one invoice; asserts all 10 return the *same* payment id and the invoice is credited exactly once (`amountPaid === '100'`), never ten times.
- `clinical-workflow.e2e-spec.ts` — the Phase 4 analogue of `hospital-workflow.e2e-spec.ts`, picking up exactly where Phase 3's flow leaves off (appointment `IN_CONSULTATION`): doctor starts an encounter (asserting a `NURSE` is forbidden from starting one) → nurse records vitals → doctor adds a clinical note, a diagnosis (draft → finalize), and a prescription (draft → finalize) → doctor orders a lab test → lab tech A collects the specimen and enters a result → lab tech A's self-verification attempt is rejected (`403 SELF_VERIFICATION_FORBIDDEN`) → lab tech B verifies it → pharmacist dispenses the full prescribed quantity (asserting the stock batch decremented) → doctor completes the encounter (asserting the appointment syncs to `COMPLETED`) → accountant creates an invoice mixing a catalog service and a free-form line item, issues it, records a full payment (asserting `PAID`), then a partial refund (asserting `PARTIALLY_PAID`). Every step asserts state before advancing, same discipline as the Phase 3 workflow test.

Phase 5 additions — HospitalOS Connect's own IDOR/concurrency/journey coverage, the one dimension Phases 1-4's suites never needed (a patient-vs-patient ownership check, not a hospital-vs-hospital one):

- `connect-idor.e2e-spec.ts` — Connect Patient A vs Connect Patient B across every new resource: appointment read/cancel/list, medical records (encounters/prescriptions/lab-orders/invoices), and record-claiming (the generic anti-enumeration error, and a double-claim rejected with the same error). Also a quick public-discovery sanity check (no auth at all).
- `connect-concurrency.e2e-spec.ts` — 100 simultaneous self-registrations (no crashes, no duplicate accounts), 50 simultaneous bookings across 50 distinct slots (no cross-talk), 10 simultaneous bookings for the identical doctor+slot (exactly 1 succeeds), a concurrently-retried idempotency key (exactly 1 appointment, every response returns it), and 10 simultaneous claims on the same unclaimed record (exactly 1 succeeds) — the last one is the direct regression test for the claim-record race fixed during the database-integrity audit, see `/DECISIONS.md`.
- `connect-patient-journey.e2e-spec.ts` — Scenario B of the final E2E list: one continuous story, no pre-existing account, discover → register → book → get checked in → get called → get seen (encounter, diagnosis, finalize) → read the resulting finalized record back through her own session. Same one-continuous-run-asserting-every-step discipline as `hospital-workflow.e2e-spec.ts` (Scenario A) and `clinical-workflow.e2e-spec.ts` (Scenarios C-F).
- `operations-tenant-isolation.e2e-spec.ts` — its `Role.PATIENT`-is-denied-everything setup was broken by Phase 5's `PATIENT_SELF_REGISTRATION_ONLY` change (staff could no longer create a `PATIENT`-role user via `POST /users`) and was fixed to register through Connect instead; see `/DECISIONS.md`. Caught during the Phase 5 tenant-isolation audit, not by a failing run (this suite has never executed here either).

## Not yet covered

- Load/performance testing at real production scale — the concurrency e2e tests use deliberately-sized concurrency (10/50/100-way, matching the Phase 5 master doc's own numbers), not a sustained load test. No load-testing tool (k6, Artillery, etc.) is wired in.
- Frontend automated tests (component/E2E-in-browser) — `apps/web` was manually verified in a real browser against a real (unreachable, by design in this environment) API in Phase 2/3, and again in Phase 5 for the two login/`useRequireAuth` role-guard changes (verified live via `npm run dev` + browser automation — confirmed the `?blocked=patient` message renders and the normal login form is unaffected when absent, see `/DECISIONS.md`). No Playwright/Cypress suite exists yet. **No HospitalOS Connect frontend exists** — Connect stays API-only on the frontend side this phase, same backend-first precedent Phase 4 established; see `/DECISIONS.md`.
- `DoctorUnavailability` has no dedicated unit or e2e test beyond what `getAvailableSlots`'s tests exercise indirectly (an unavailability window excludes the slots it overlaps) — no test for creating/listing unavailability via the HTTP endpoints themselves.
- `DispenseService#returnStock()` has no dedicated e2e test (unit-tested only) — see the known gap noted in `/SECURITY.md` about cumulative-return tracking.
- `LabResult`'s `REVIEWED` status and `StockMovementType.TRANSFER` are unreachable via any endpoint and therefore untested beyond type-level existence — reserved for future granularity, same pattern as `AppointmentStatus.CHECKED_IN` in Phase 3.
- No automated accessibility-audit tool (axe-core, Lighthouse CI) is wired in — the Phase 5 frontend audit was manual (static analysis + one live browser check), not tool-assisted.
